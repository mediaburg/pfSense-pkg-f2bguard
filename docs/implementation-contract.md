# Implementation contract: pfSense Fail2Ban Guard

First implementation, no automatic permanent escalation. Python 3.11+ standard library only for service and Linux sender. Native pfSense PHP pages and package integration. All default-disabled; no new listener or rule until configured explicitly.

## API

HTTPS mTLS only. Config binds to an explicit IP, never wildcard. Authenticate SHA256 of DER client certificate against `clients` list: `[{"id":"server-a","cert_sha256":["64hex"],"allowed_jails":["recidive"]}]`. Unknown clients denied. Clients cannot change policy or other clients. TLS private key not returned via any endpoint.

POST /v1/events: {"events":[{"event_id":"uuid","seq":1,"op":"ban","jail":"recidive","ban_id":"uuid","ip":"203.0.113.1","permanent":true,"expires_at":null}]}. unban has same identifying fields, new event_id and increasing seq, no requirement for permanent. All identifiers constrained. Sequence strictly increases globally per authenticated client and persists across restarts. Duplicate retries have no effect; old events never resurrect claims. Each ban is identified by client+jail+ban_id and canonical IP. Non-permanent bans are not enforced in strict mode. Only IP literals, no subnets/hostnames. Unban affects matching client's exact claim only. Multiple clients' claims are unioned.

POST /v1/snapshot: {"snapshot_id":"uuid","seq":99,"claims":[{"jail":"recidive","ban_id":"uuid","ip":"203.0.113.1","permanent":true,"expires_at":null}]}. Authoritative complete state for authenticated client at seq boundary; atomic replacement, older snapshot ignored, duplicate safe. Never infer unban from client silence. Sender serializes full snapshots and events with a single durable sequence allocator. Snapshot may be omitted by endpoint until reliable enumeration available; clearly report this as degraded, never send empty on enumeration error.

GET /v1/status returns only this client's status, no secrets or other clients' IPs. API response for successful write includes accepted true, effective IP count; HTTP 4xx for invalid request and 503 for enforcement failure. Idempotent durable writes with periodic retry of local enforcement.

## Config

JSON /usr/local/etc/f2bguard/config.json, root-owned 0640.
{"enabled":false,"listen":"127.0.0.1","port":9443,"tls":{"cert":"...","key":"...","ca":"..."},"clients":[],"database":"/var/db/f2bguard/state.sqlite","whitelist_file":"/usr/local/etc/f2bguard/whitelist.txt","enforcement_socket":"/var/run/f2bguard/pf.sock","limits":{"body_bytes":1048576,"events_per_request":1000,"claims_per_client":10000,"requests_per_minute":120},"history_days":90}
Whitelist file is trusted resolved IP/CIDR lines generated by privileged pfSense integration. Initial absence or invalid content blocks new enforcement; preserve last valid whitelist and applied tables. Whitelist overrides claims, no pass rules. History records only; never reban from history.

## PF helper protocol (root implementation)

Unix socket newline-delimited JSON, maximum 4 MiB: {"op":"replace","ipv4":["..."],"ipv6":["..."]}. Reply {"ok":true} or {"ok":false,"error":"..."}. Fixed tables f2bguard_v4 and f2bguard_v6 only. Validate canonical single IPs and enforce whitelist again. Never shell=True; pfctl argv only, IPs on stdin. Peer UID must be configured f2bguard service user. No client-chosen command, table, path, or interface. Status from daemon must distinguish durable desired claims and successfully applied tables.

## Layout / ownership
Core agent owns src/f2bguard/{__init__,config,store,server}.py and tests/test_core*.py.
Client agent owns client/ and tests/test_client*.py. CLI event enqueue must remain offline and durable, sender workers handle HTTPS and retries. Certificate verification is mandatory, no insecure option.
pfSense UI agent owns pfsense/ and docs/pfsense-integration.md. Native forms, tabs, CSRF/auth through pfSense, escaping, strict config validation. No claiming FRP exact style verified (source unavailable).
Root owns src/f2bguard/pf_helper.py, service CLI wiring as necessary, integration tests, docs/README, security review. Coordinate before changing another owner's files.

## HA
Must not claim CARP/pfsync syncs package DB. Native HA handles static package configuration only if explicitly integrated. Own runtime claim replication required. Any unimplemented automatic failover/replication is an explicit release blocker for HA production, not silently ignored. No unsafe dual writer.
